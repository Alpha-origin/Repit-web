# 실패한 피드백 재채점

- 이슈: #153
- 기준: `dev` `bb60220` (#147의 재채점 수정 요청 후속)
- 범위: 종합·상세 피드백의 FAILED 재시도. 서버 계약 변경 없음.

## 사용자 흐름

1. 피드백 화면 진입 시 기존 결과를 조회하고, 결과가 없으면 생성을 요청한다.
2. FAILED의 "다시 시도"는 `POST /api/feedbacks?interviewId=…`로 재채점을 요청한다.
3. 접수 중에는 버튼을 비활성화하고 "요청 중…"을 표시한다.
4. PENDING으로 접수되면 기존 5초 폴링을 새 5분 기한으로 시작한다.
5. 완료되면 결과를 표시하고, 실패하면 다시 시도할 수 있다.

409 응답은 다른 요청이 먼저 접수됐거나 결과가 이미 완성된 경우로 보고 한 번 조회한다.
조회 결과가 PENDING이면 폴링하고, SUCCEEDED이면 결과를 표시한다.
조회 결과가 없으면(404) FAILED를 유지하고 상태 확인 실패 문구를 표시한다. 다시 누르면 재채점을 요청한다.
그 밖의 재요청 오류는 FAILED를 유지하면서 새 오류 메시지를 우선 표시한다.

## 요청과 화면 수명

- 최초 조회·생성의 중복 방지와 POST의 중복 방지를 각각 유지한다.
- 최초 생성과 명시적 재채점은 같은 POST 요청 함수를 사용한다.
- 같은 면접의 POST가 진행 중이면 기존 Promise를 공유한다.
- 빠른 연속 클릭은 훅에서도 즉시 차단한다.
- 면접 변경·재조회·화면 이탈로 무효가 된 응답은 화면에 반영하지 않는다.

면접 정보 조회 오류의 재시도와 피드백 목록 재조회는 기존 동작을 유지한다.
5분 지연 상태의 버튼도 우선 재조회하며, API가 FAILED로 정리한 뒤 다시 눌러야 재채점된다.

## 검증

```sh
npm run lint
npm run build
# 별도 터미널에서 npm run dev 실행 후
node tests/feedback-polling.browser.mjs
```

외부 Playwright는 `PLAYWRIGHT_MODULE_PATH`, 브라우저 실행 파일은
`BROWSER_EXECUTABLE_PATH`, 서버 주소는 `INTERVIEW_TEST_ORIGIN`으로 지정할 수 있다.
API는 모의 응답으로 검증하며 실제 분석 서버를 호출하지 않는다.

브라우저 검증 범위: 종합·상세 재채점 완료, 409 후 진행 중·완료·결과 없음 분기,
500 후 오류 표시·재요청, 중복 클릭·요청 중 버튼 잠금, 최초 생성,
접수 응답 FAILED, 면접 전환 뒤 늦은 응답 무시, 기존 폴링·기한·화면 이탈.
